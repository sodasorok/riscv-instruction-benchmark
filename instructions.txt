# про vle*/vse16.v/vlseg2e16.v/vsseg2e16.v: буфер статический и
# никогда не меняется, а ITERATIONS известен на этапе компиляции —
# поэтому GCC на -O2 способен ЦЕЛИКОМ свернуть цикл в константу (не
# просто вынести обращение за цикл, а вычислить финальный результат
# аналитически, раз всё предсказуемо).
# Первая попытка (индекс через volatile-счётчик voff++) свернуть цикл
# не давала, но сам round-trip volatile-скаляра (чтение+инкремент+запись
# в память при каждом вызове) стоил ~10 тактов и забивал измеряемую
# инструкцию собственным шумом (все vle8/16/32 давали одинаковые ~10
# тактов независимо от ширины элемента — явный признак, что меряется
# не то). Поэтому вместо voff используется compiler barrier
# `asm volatile("" ::: "memory")` перед каждым обращением — он НЕ
# генерирует ни одной инструкции (просто запрещает компилятору
# переупорядочивать/сворачивать обращения к памяти через эту точку),
# то есть не добавляет собственных тактов, но не даёт GCC доказать,
# что 10 млн одинаковых загрузок/записей эквивалентны одной.
#
# про vle*/vlseg2e16.v: адрес не меняется между итерациями,
# поэтому "Latency" для них — это НЕ настоящая latency load-to-use
# (нет истинной RAW-зависимости через адрес), а скорее back-to-back
# issue rate одного и того же адреса (вероятно, попадёт в L1). Честная
# latency загрузки — это отдельный тест "pointer chasing"
